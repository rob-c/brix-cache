## Method

1. **Directive census.** `tools/ci/check_directive_registry.py::collect()`
   enumerated every `ngx_command_t` registration in `src/`:

   | Measure | Count |
   |---|---|
   | Registrations | 723 (2026-09-09, after F1-F9; 721 after F1-F7 on 2026-09-08; 719 on 2026-09-07) |
   | Unique directive names | 585 (F9 added `brix_sss_getcreds` and `brix_tap_proxy_sss_identity` on the stream plane; 583 after removing `brix_pss_dca` and `brix_backend_passthrough_persist`; phase-115 added `brix_cms_response`, `brix_upstream_x509_proxy`, `brix_upstream_x509_key`, `brix_frm_purge_max_bytes`, `brix_oss_space`, `brix_cache_serve_while_filling`; also registered by 2026-09-07 15:40 and not named earlier in this row, all stream-plane: `brix_cms_admin_socket`, `brix_cms_coalesce`, `brix_cms_space_enforce`, `brix_cms_space_hwm`, `brix_tap_proxy_path_rewrite`, `brix_tpc_outbound_renew_lead`, `brix_tpc_outbound_renew_strict`) |
   | Registered on the http plane | 323 |
   | Registered on the stream plane | 396 |
   | Literal `ngx_string("…")` registrations | 655 |
   | Macro-expanded registrations | 64 |
   | Allowlisted registry exceptions | 30 |

   For every unique name three questions were asked mechanically and then
   confirmed by reading the code:
   - **Consumer:** is the field the setter writes (`offsetof(…, field)`, or
     the custom setter's target) read anywhere in `src/` outside
     `src/core/config/`, the `directives_*.h` tables and the
     `*conf_fields*.h` / `conf_structs.h` declarations? A read only in
     create/merge counts as *no consumer*.
   - **Test:** does any file under `tests/` (`.py`, `.conf`, `.j2`, `.tmpl`,
     `.yaml`) contain the directive name as a whole word?
   - **Docs:** does the name appear as a whole word anywhere under `docs/`
     other than `docs/refactor/`, `docs/doxygen/` and the generated table in
     `directives.md` (between the `BEGIN/END GENERATED DIRECTIVE REGISTRY`
     markers)?
2. **Feature census.** Every MISSING / PARTIAL row of the parity audit and
   every "gap" row of the four `10-reference` documents was re-checked
   against the source tree for a directive, a handler or a test that would
   contradict it. Two contradictions were found and corrected (see (d)).
3. **Ghost census.** Every `brix_*` token in `docs/` (excluding
   `docs/refactor/`) was checked against the registry; a token that names no
   registered directive is a ghost. Five were found (see (d)).
4. **Guard.** The (c) and (d) findings are pinned by
   `tests/test_release20_directive_surface.py` so the register cannot rot
   silently: a new registration without prose, an accepted-only knob not
   named here or not labelled in `directives.md`, or a removed directive
   that parses again, fails the PR tier.

*registered* directives nothing reads. This one asks the mirror question —
which **implemented config surfaces nothing registers**. A setter, a config
field, a merge default, a runtime reader and header prose can all exist while
no `ngx_command_t` entry names the directive: `nginx -t` then answers `unknown
directive`, and the code reading the field only ever sees the merge default.
The defect is invisible to a reader of the source, because every part of the
feature is present and correct.

The audit was mechanical (`ngx_command_t` census × every `brix_conf_set_*`
setter and every documented `brix_*` name in a header comment) and found three
instances plus one diagnostic-level cousin. All four are fixed in 2.0.

### (c.4) Registered but never armed — the layer under (c.3)

Found 2026-09-09, immediately after (c.3), by asking what changed when the
Pelican family was finally registered: **nothing**. The directives parsed, the
fields were written, the merge ran — and the per-worker scheduler still
declined on every start, because the gate it consults reads a *different*
field, one that no directive can write.

This is (c.3) one layer deeper, and it is worse in exactly one way: `nginx -t`
cannot see it. A registered-nowhere directive at least fails loudly at parse
time. A registered-but-never-armed feature accepts its configuration, logs
nothing, and stays off forever — the operator's config file is the strongest
possible evidence that the feature is on.

Every instance in this tree had the same origin. `brix_cache_origin{,_tls,…}`
was retired in phase-64 §14 (a cache's source became the export's
`brix_storage_backend`, its identity a named `brix_credential`), but four
fields survived the deletion of their directives because `sd_xroot` — and
`gsi_upstream_login` — build a **synthetic** `ngx_stream_brix_srv_conf_t` as
the parameter block for the in-process origin wire client. On a synthetic conf
`cache_origin_host` / `cache_origin_port` are the origin endpoint. On every
real server conf they are empty forever. Six live readers had not noticed.

| # | Site | Feature | Symptom before 2.0 | 2.0 |
|---|---|---|---|---|
| D1 | `fs/cache/origin/pelican_register.c` | Pelican advertiser | the scheduler's `cache_origin_host.len == 0` gate declined on every worker start, and the `.well-known/pelican-configuration` URL was built from the same empty host — so registering the family in (c.3) still advertised nothing | new `brix_cache_advertise_federation <host[:port]>` (the family's **eighth** name) writes `advertise.federation`; the gate and the discovery URL both read it |
| D2 | `fs/cache/thread.c` | cache-bypass redirect | an object the admission policy declined (too large to cache) answered `kXR_Unsupported` — "no origin configured for redirect" — instead of redirecting the client to the origin. The XrdPfc behaviour this imitates never fired once | `brix_cache_bypass_redirect()` resolves the endpoint from the task's `source_inst`, the export's registered `root://` backend, via the new `brix_sd_xroot_endpoint()` accessor; the error is now reached only when no endpoint can be named (http/local backend, or a `forward://` instance whose endpoint the client names per open) |
| D3 | `protocols/root/query/checksum_qcksum_path.c` | `kXR_Qcksum` by path, on a cache miss | the miss branch was entered and then could never redirect, so a checksum query for an uncached path answered "not found" on a working read-through cache | resolves the backend through `brix_vfs_backend_resolve(root_canon)` + `brix_sd_xroot_endpoint()` and redirects |

Two operator-facing messages had the same disease one level out, and are
fixed with them: the `brix: cache enabled … origin=%V` start-up NOTICE printed
the always-empty retired string (it now prints `brix_storage_backend`), and the
origin TLS refusal told the operator to "enable `brix_cache_origin_tls`", a
directive retired two phases earlier (it now says to use a `roots://` URL in
`brix_storage_backend`).

**The durable part** is not the six fixes; it is the guard. The four orphaned
fields are now documented in `srv_conf_fields_net.h` as synthetic-conf-only,
with a pointer to `brix_sd_xroot_endpoint()` as the supported way to learn a
backend's endpoint from a real conf, and
`test_no_new_reader_gates_a_feature_on_an_unwritable_field` holds them to the
five files that legitimately touch them — the declaration, the two synthetic
writers, and the two wire-client readers. A seventh site cannot be added
without failing that pin.

Pinned by `tests/test_release20_never_armed.py` (28 tests): the federation
grammar (4 accepted spellings; scheme / path / port 0 / port 70000 / both

`no_resolve` deferral required by INVARIANT 13, a per-site pin for D1-D6, the
two message fixes, the class guard and its allowlist-existence pin, the
"retired directives stay unregistered" contract with a config-level
security-negative, and the prose pins for this section and for
`docs/03-configuration/directives.md`.

### (c.5) Computable but never advertised — the same disease on a list

Verifying a (c.2) doc row surfaced one more instance of the (c.4) shape, this
time not on a config field but on a **list**. `sha512` is a first-class
built-in: `brix_checksum_lookup_alg` resolves it, `brix_checksum_default`
accepts it, Qcksum computes it, WebDAV answers `Digest: sha512=<hex>`. It was
absent from exactly one place — `brix_qconf_chksum_algs`, the array behind the
Qconfig `chksum` cslist, which is the list every WLCG client intersects to pick
an algorithm. Worse, `qconf_chksum_default_known()` decided whether the
operator's `brix_checksum_default` was answerable by walking that same short
array, so:

| Configured | Qcksum answers it? | Advertised? | What a client did |
|---|---|---|---|
| `brix_checksum_default sha512` | yes | **no — silently dropped** | negotiated `adler32` |
| `brix_checksum_default crc64xz` (documented alias of `crc64`) | yes | **no — silently dropped** | negotiated `adler32` |

Both are configurations `nginx -t` accepts, that compute correctly on every
per-request path, and whose only failure is that no client ever asks for them.
The fix is one line plus one resolver swap: `sha512` joins the advertised
array, and `qconf_chksum_default_known()` now asks `brix_checksum_parse()` —
the *same* resolver `checksum_qcksum.c` uses to honour the default — instead of
keeping a private list that could drift from it again. Alias spellings are
advertised as written, since that is the name the operator chose and the server
genuinely answers it. An unanswerable default is still dropped, never echoed:
the advertisement may not claim more than the server can compute.

Pinned by six tests in `tests/test_release20_checksum_plugin.py` (32 total):
`sha512` leads the list and Qcksum returns the reference digest, an alias
default leads while the canonical spelling stays on offer (success);
`blake3` is dropped and `adler32` heads the list (error); naming an
unregistered plugin as the default neither advertises it nor makes Qcksum
answer it (security negative — operator input reaching an emitter must never
widen the server's claims); and two durable pins —
`test_every_non_alias_builtin_is_on_the_advertised_list` parses
`brix_checksum_lookup_alg`'s own table, folds aliases by enum value, and
requires set equality with the advertised array, so a future built-in that
skips the cslist fails immediately; `test_the_default_gate_asks_the_shared_resolver_not_a_local_list`
forbids the private-list regression by name.

polices metric names**. `check_metric_names.py` proves every `brix_*` family a
doc cites against ground truth parsed out of the C exporters, and it read four

the safety property — a tree-wide cross product would bless hundreds of
families no exporter emits. Three tests in `tests/test_ci_guards.py` pin it:
`test_metric_names_extractor_resolves_a_prefix_composed_family` (all eight, off
the live tree), `test_metric_names_guard_still_catches_an_invented_composed_suffix`
(a suffix the file never renders stays unknown) and
`test_a_composed_prefix_never_leaks_out_of_its_own_file` (a log tag in another
file composes nothing).
