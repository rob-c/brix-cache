Architecture · the storage seam

Every byte crosses one line.

Five protocol front ends. Eleven storage drivers. One API between them — and a CI guard that fails the build if anything tries to go around it. This is the layer that lets root://, WebDAV, S3, CVMFS and GridFTP share a namespace with POSIX, Ceph, object stores, remote origins and tape without any of them knowing about each other.

Why it exists

Five protocols times eleven backends is not fifty-five problems.

A server that speaks five wire protocols over a dozen storage systems has an obvious failure mode: each protocol grows its own open(), its own path confinement, its own metrics, its own cache awareness — and they drift. The escape check hardened on the HTTP PUT path never reaches the kXR_mv handler. The byte counter that landed on root:// reads never lands on S3 GET.

The VFS collapses that grid. A handler's entire relationship with storage is: fill in a request descriptor — export root, resolved path, caller identity, write permission, TLS flag, cache config — and call one function. It gets back an opaque handle or a buffer chain to frame onto the wire. It never sees a raw file descriptor except through an accessor, and it never learns which backend answered.

Adding a protocol costs one context struct. Adding a backend costs one vtable. Neither one touches the other, and neither can quietly skip a security check.

That is the leverage. A new storage backend arrives with metrics, access logs, confinement re-checks, page checksums and cache eligibility already working across all five protocols, because none of that lives in the backend or in the protocol. It lives in the seam.

the storage seam
Concurrency

One seam, two thread-safety contracts.

Metrics allocate. Access logs allocate. nginx request pools are not thread-safe. So the metered API can only run on the event loop — but hot reads and writes have to run off it, or the worker stalls behind the disk.

event loop only

The metered surface

brix_vfs_open, read, write, stat, rename and the rest. These allocate from the request pool, bump a Prometheus counter and emit an access-log line — which is exactly why protocol handlers do not emit their own per-operation data-plane metrics. They get them by calling the seam.

any thread

The execute core

brix_vfs_io_execute() takes a plain-old-data job descriptor and mutates only its output fields and caller-owned buffers. No pool, no metrics, no log, no cache state. It is the same body whether it runs inline on the loop, on an AIO thread-pool worker, or on the io_uring fallback.

The resolution is not two implementations — it is two entry surfaces over one shared body. Before this split the thread-pool workers carried their own copies of the read, write, readv and pgread syscalls, so confinement, CRC handling, short-I/O policy and error mapping could drift between the worker and the VFS. They cannot now. There is one body, and the only rule a caller has to remember is which surface it is allowed to touch.

Capabilities

Backends declare what they are. They never lie by omission.

An object store has no file descriptor, so it cannot sendfile. A read-only origin has no write path. A tape backend can stall for minutes. Rather than let the VFS sniff for backend identity, every driver publishes a capability bitmap and the VFS branches only on bits — a rule a CI guard enforces by rejecting identity comparisons outright.

Absence is the safety mechanism

The cephfsro driver serves a real CephFS filesystem by decoding its on-RADOS structures directly, and it is meant to be read-only. It fills thirteen of the vtable's fifty-one slots — init and cleanup, open and close, the two reads, the two stats, directory iteration, two xattr readers — and leaves every mutating slot NULL. It therefore cannot be selected as a writable export primary. Nothing checks a flag at request time; the function pointer is simply not there.

Caches and staging areas are drivers too

A read-through cache in front of a remote origin is not special-case code inside the read path. It is a driver that wraps another driver and presents the same vtable upward: the VFS holds one instance and never learns it is talking to a decorator. The same mechanism backs write-back staging in front of tape and proxy write-through to a remote root:// primary. A site changes its storage topology by changing a directive, not by recompiling a data path.

Confinement

The seam is where the escape check actually happens.

Four invariants hold at every entry point, for every protocol, on every backend — because there is only one place left to put them.

Re-check, never trust

Path resolution happens above the seam. The VFS does not take its word for it: every entry point re-verifies that the resolved path is non-empty and carries its confinement flag before any syscall runs. Two independent gates, and both must hold.

The kernel enforces the boundary

The confined open is openat2(RESOLVE_BENEATH) against a persistent per-worker root descriptor — not a string comparison on .. that a symlink can defeat. An EXDEV coming back is not a filesystem quirk, it is a traversal attempt, and it surfaces as kXR_NotAuthorized or HTTP 403.

Writes fail closed

Write permission is checked after confinement and before any mutation; a write open is refused up front with EACCES. This is the data-plane backstop sitting behind the protocol-layer write gate, not a replacement for it.

TLS and cleartext buffers never mix

A TLS connection, or a request that wants page checksums, gets a memory-backed buffer; cleartext gets a file-backed buffer so the kernel can sendfile it. One chokepoint decides, which is why a file-backed buffer cannot reach a TLS connection.

The seam also knows where to stop. It confines to one export root and, under impersonation, resolves as the mapped user — which is exactly wrong for a cache root, an upload staging directory, a tape control journal or an S3 multipart spool. Those are service-owned domains under a different root, and routing them through the VFS would open the wrong root as the wrong identity. So they stay raw, deliberately, each behind a same-line /* vfs-seam-allow: reason */ marker. There are 87 of them, every one is a documented decision, and the guard refuses to let an unmarked one appear.

Enforcement

An architecture nobody can quietly walk around.

Every layering claim on this page is worth exactly as much as its enforcement. A convention that lives in a README decays on the first deadline, so the seam is checked by tools/ci/check_vfs_seam.py on four fronts — three through the server, one across the client tree. Each carries a migration backlog: the grandfathered files allowed while the codebase converged, which the guard permits and never lets grow. Both server backlogs are empty. One client file is left.

Tier What it catches Rule Backlog
tier-1 A raw positional byte op — pread, pwrite, copy_file_range, sendfile — anywhere outside src/fs/backend/. hard fail, no backlog —
tier-2 A handler reaching past brix_vfs_* into the confined-helper layer or the driver vtable directly. grandfathered 0 files
tier-3 A handler making a raw namespace or metadata syscall on storage — open, stat, opendir, unlink, rename, mkdir, chmod, xattr. per-line marker required 0 files
client A raw byte op in the native client tree, which links the lower half of the seam but has no confined server root above it. grandfathered 1 file

The guard strips comments and string literals before matching, so an operation name mentioned in prose is never a false positive — and it reads the allow-marker off the raw line first, so a real exception is never a false negative. A separate guard forbids the VFS from branching on backend identity rather than capability, so the polymorphism cannot rot into a chain of name comparisons.

The layering is not documentation. It is a build failure.

Identity

The caller's identity survives the hop to the backend.

A frontend that authenticates a user with an X.509 proxy and then writes to its origin as nobody has thrown away the point of authenticating. The seam carries a per-open credential down to the driver, and each driver declares which kinds it can actually present to its origin.

Credential kind How the backend leg authenticates Drivers that accept it
BEARER Replay or exchange a WLCG / JWT bearer token xroot · remote · http
PROXY_PEM Present a full X.509 proxy — pre-provisioned, delegated, or minted from a local CA xroot · remote · http
IDENTITY Principal and VO list only — no forwardable secret is needed or minted pblock
SSS Re-issue an XrdSecsss credential asserting the caller, signed with a gateway keytab xroot
S3 Trade the node credential for an STS session keypair scoped to the caller remote
GSS_KRB5 Forward the delegated TGT through a multi-leg GSSAPI negotiation xroot

The accepted-kind mask is a gate, not a hint. If the live credential kind is not in the driver's set, the VFS denies with EACCES before the origin is contacted — no silent downgrade to the service account, and no accidental privilege gain from a backend that would have accepted anything it was handed. See per-user credential forwarding for what that buys at the protocol edge.

The bottom of the seam ships in the client tools

The verb kernel, the driver vtable and the S3 signing and transfer kernel are compiled free of any nginx dependency and linked into the native clients as well as the server, so xrdcp and its siblings move bytes through the same code the server does. The divergence is deliberate and narrow — the server's confined open and staged commit must never appear on the client's unconfined paths.

Adding a backend is a checklist, not an excavation

Write the driver, append one row to the central census header, register its sources, declare its capabilities honestly, and ship a byte-exact round-trip test plus one security negative. The registry table, the extern declarations, the store-URL scheme table and the per-backend metric labels all generate from that single row — there is no fourth place to forget.
