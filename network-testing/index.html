Network testing

Test every network condition before users meet it.

Even well-managed infrastructure can see early disconnects, long stalls, or changed bytes. BriX-Cache ships a fault-injection tool so you can reproduce those conditions on demand and confirm that each transfer either completes with the right data or reports a clear error.

The threat model

Two questions every transfer must answer.

A closed connection does not by itself prove a successful transfer. Length framing answers how many bytes, not which bytes. Every write path therefore answers two separate questions about completion and integrity.

Q1

What confirms the transfer finished completely?

An idle timer is not a deadline. A slow-drip adversary that sends one byte per timeout − ε can keep a connection open indefinitely. A logical operation needs an absolute deadline across the whole operation, and a positive signal that the last byte is really the last byte.

Q2

What confirms the bytes match the source?

Integrity has a direction. “Verify on ingest” plus “verify on read” still leaves the outbound commit leg — the gateway writing to its own origin — completely naked, and it is the hop most easily forgotten because it feels internal. Prefer a peer-validated inline header that fails the write closed over a post-commit probe that races.

The posture, in one line: new-integrity surfaces are opt-in knobs; clear bugs fail closed.

The instrument

Network faults, on demand.

brix-fault-proxy is a root-free, userspace TCP relay that you place in front of any BriX-Cache, stock XRootD, or HTTP endpoint. It needs no CAP_NET_ADMIN, no tc, no netem: just --listen, --target, and a loopback --control port you drive live.

The expected result stays simple: the bytes that arrive match the published data, or the transfer returns a clear error. Corrupt data and incomplete reads are never reported as successful.

# data-plane black hole — client must not corrupt
The levers

Every way a wire goes wrong.

Each lever is off by default and — for the byte-level ones — per-direction (up = client→upstream, down = upstream→client). Set them at launch with --<lever> flags, or live by writing one newline-terminated command to the control port.

latency <ms>

Delay every forwarded chunk — a high-RTT link.

jitter <ms>

Random 0..ms delay per chunk — the application-visible signature of IP reordering.

chunk <bytes>

Split writes into ≤N-byte segments so the peer sees genuine partial reads.

drip <bytes> <ms>

Forward N bytes, sleep, repeat — a Slowloris slow-drip.

rate <KB/s>

A hard bandwidth ceiling.

corrupt <pct>

Flip a random bit in pct% of forwarded bytes — a real in-band MITM mutation.

lossy <pct>

Per-chunk probability to sever the stream (loss modelled as a reset, not a byte drop).

reorder <pct> [ms]

Hold back a fraction of chunks by ms.

dup <pct>

Deliver a fraction of chunks twice.

truncate-at <bytes>

A deterministic mid-transfer cut once N bytes have flowed that direction.

fail-nth <n>

Fail exactly the Nth accepted connection.

heal-after <ms> · one-shot

Auto-clear all levers after ms, or self-heal the instant the next sever fires.

drop · reset · half-close

FIN- or RST-sever every live connection now; or FIN the up path while down keeps flowing.

hang · block

Black-hole (accept but never relay) or full outage (drop live, refuse new); unhang / unblock to resume.

How the model works. Packet loss is modelled as a connection sever, not a byte drop — dropping bytes from an already-ACKed TCP stream corrupts it rather than emulating loss. True out-of-order packet delivery can’t be faked either, since TCP reassembles in order, so jitter and reorder inject the variable latency reordering imposes. corrupt, by contrast, is a real in-band byte mutation — exactly what an application-layer checksum exists to catch.

How it compares

Where this sits among evil-actor proxies.

Inline adversarial proxies split into a few well-known classes, each pitched at a different layer. The point below is not that one wins — it is which question each is built to answer, and why a storage gateway’s integrity question needs a purpose-built L4 instrument.

Kernel packet emulators

tc / netem · Pumba · Comcast · WANem

L3 packet qdisc — root / CAP_NET_ADMIN

Best at. Faithful WAN physics: real loss, reorder, duplication and rate applied to every packet on a NIC or network namespace. Nothing else models the transport layer as honestly.

Where it stops. Blind to the application. It cannot cut a transfer at exactly 5 MiB of payload or flip a byte at a chosen stream offset — and its packet-level corrupt is usually caught by the TCP checksum and retransmitted, so the mutation rarely reaches the app it means to stress. Global to the interface, and it needs privilege.

L4 chaos proxies

Toxiproxy · Muxy · Blockade

L4 TCP stream proxy — userspace

Best at. Language-agnostic “toxics” — latency, bandwidth, slice, timeout, reset — behind an HTTP control API. Excellent for CI fault-injection of a service’s dependencies.

Where it stops. Toxics are generic stream perturbations. None models a silent in-band bit-flip that survives to the application, per-direction control is coarse, and the design targets microservice RPC rather than the completion-and-integrity gates of a binary storage protocol.

L7 intercepting / MITM proxies

mitmproxy · Burp Suite · OWASP ZAP

L7 HTTP / TLS — userspace (own CA breaks TLS)

Best at. The gold standard for HTTP security work: decrypt TLS, rewrite or fuzz any request and response, replay, script arbitrary tampering.

Where it stops. HTTP-shaped and heavyweight. They do not speak raw root:// or GridFTP MODE E, and tampering is imperative scripting — not a declarative, reproducible transport-fault matrix you can pin a regression test to.

brix-fault-proxy

this repository · one static C binary

L4 byte-stream relay — root-free userspace

Best at. Per-direction byte-level levers with deterministic, offset-tied truncation and a real in-band bit-flip that reaches the application intact — the exact stimulus an application checksum must catch. Live loopback control, protocol-agnostic across root://, HTTP, S3 and gsiftp.

Honest limit. Honest limit: it reassembles TCP in order, so it models packet loss as a connection reset and cannot inject true out-of-order packet delivery — that stays netem’s job. It answers the byte-integrity question, not the packet-physics one.

Complementary, not ranked. Reach for netem when you need faithful packet physics; reach for an L7 MITM to fuzz HTTP semantics. brix-fault-proxy owns the middle — a privilege-free, per-direction, offset-deterministic instrument for the one thing a storage gateway must never get wrong: did the exact bytes arrive, and was a corrupt or short transfer ever reported as success?

What it caught

Real bugs found and fixed through fault injection.

Each issue below came from a real completion or integrity gap found during the write-path review. Every fix now has a dedicated regression test.

#1

A truncated fill served as a complete hit

A mid-transfer cut on the origin→cache link left a short .part that was committed and served forever as a complete object. Now the fill spine refuses to commit a fill shorter than the known object size.

tests/test_cache_truncation_poison.py

#6

A WebDAV PUT that never checked its own digest

A byte flipped in flight — with a valid RFC-3230 Digest / Content-MD5 present — returned 201 and committed poison. Now the asserted digest is verified over the staged bytes before publish, and a mismatch fails 400 BadDigest.

tests/resilience/test_webdav_put_corruption.py

#8

A GridFTP MODE E hole answered as 226 complete

A flipped 17-byte EBLOCK offset (or a short sender that still emits EOD) left a zero-filled gap reported as a complete transfer. Now the accepted ranges must tile [0, high-water) gaplessly, or it is 550 and the file is unlinked.

tests/test_gridftp_mode_e_truncation.py

#13

A third-party pull with no end-to-end check

Native TPC committed both truncated and corrupted pulls as complete. Now an always-on source-size completion gate runs, with an opt-in post-copy checksum on top.

tests/test_tpc_pull_integrity.py

Status, stated plainly: the tool itself is a first-class, tested client binary. The integrity fixes above were found and closed in the write-path hardening sweep; several are recent and land alongside their gate tests rather than in a tagged release.

The suites

Byte-exact results under every tested fault.

The proxy is wrapped by a FaultProxy harness in tests/resilience/ and driven across the storage estate. The invariant is uniform everywhere: never exit 0 with corrupt or short bytes; zero silent EIO / kXR_IOError surfaced as success.
