6/*
7 * carry.h — async-safe carry of a delegated krb5 credential (phase-70 §5.7).
8 *
9 * WHAT: Serialise a captured GSS initiator credential
10 * (brix_krb5_capture_fwd_cred) to a 0600 FILE ccache and re-acquire it
11 * later, so the delegated identity can cross the request → async
12 * cache-fill boundary as a plain filesystem PATH rather than a live
13 * gss_cred_id_t handle.
14 *
15 * WHY: The origin krb5 EXCHANGE leg (brix_cache_origin_auth_krb5) runs on the
16 * async fill task (worker thread, outliving the request), but a live
17 * gss_cred_id_t is request-scoped and unsafe to embed in
18 * brix_cache_fill_t. The codebase already solves this exact shape for
19 * x509 proxies — the front door writes the PEM to a 0600 temp path and the
20 * async gsi leg reloads it (vfs_deleg.c brix_vfs_deleg_proxy →
21 * brix_cache_origin_auth_gsi). This is the same pattern for krb5: a FILE
22 * ccache is the serialisable artifact, its path is the async-safe carry,
23 * and re-import happens on the fill task. The path names a temp file the
24 * caller owns (0600 via mkstemp) and cleans with the request pool.
25 *
26 * HOW: Export writes the forwarded TGT out of the initiator cred into a FILE
27 * ccache with RFC 5588 gss_store_cred_into() (overwrite=1, which
28 * initialises/overwrites the named ccache — unlike the deprecated
29 * gss_krb5_copy_ccache, which cannot initialise an empty target); import
30 * mirrors capture.c (krb5_cc_resolve FILE + gss_krb5_import_cred). All
31 * handles stay opaque
32 * (void*) so krb5/GSSAPI never leak into this header, exactly as
33 * capture.h / forward.h do.
34 */
35
